# Модель данных Denta

## Визит

Визит — единица общей хронологии. Осмотр с четырнадцатью диагнозами остаётся одним визитом.

```js
{
  id,
  type,            // inspection | treatment | surgery | hygiene | ...
  date,
  title,
  doctor,
  doctorId,
  clinicId,
  clinic,          // снимок названия для устойчивой истории
  cost,
  currency,        // { code, symbol, name }
  notes,
  attachments,     // документы, относящиеся ко всему визиту
  items: []        // записи по конкретным зубам
}
```

## Запись по зубу

Одна пакетная операция формы создаёт отдельную запись для каждого выбранного зуба. Поэтому её можно увидеть и внутри визита, и в истории конкретного зуба.

```js
{
  (id,
    batchId, // связывает записи, добавленные одной пакетной операцией
    tooth,
    kind,
    status,
    title,
    notes,
    surfaces,
    attachments); // документы только этого зуба
}
```

## Справочники

Клиники, врачи и валюты хранятся отдельно от визитов. В самом визите остаётся снимок использованного значения, поэтому переименование или удаление элемента справочника не ломает старую историю.

Врач не принадлежит одной клинике. В его справочной записи хранится список встречавшихся мест работы, а точная пара «врач + клиника» фиксируется каждым визитом. Поэтому смена клиники не создаёт второго врача и не переписывает старые приёмы.

Все справочники сохраняются в `localStorage`, входят в JSON-архив и при подключённом Firebase синхронизируются документом `users/{uid}/settings/directories`.

## Вложения

Модель уже различает вложения уровня визита и конкретной записи по зубу и поддерживает несколько файлов. Сейчас в событии сохраняются метаданные файла. Хранение бинарного содержимого потребует отдельного слоя IndexedDB/Firebase Storage и должно быть добавлено до использования вложений как постоянного архива.

## Доступ врачу

Публичная временная выписка формируется как отдельный снимок медицинских данных. Поля `cost` и `currency` удаляются из визитов и вложенных записей до сохранения публичной ссылки. Стоимость остаётся только в личной истории и полном пользовательском архиве.

## Совместимость

Старые плоские события с полем `tooth` продолжают читаться через адаптеры `eventEntries()` и `flattenDentalEntries()`. Одномоментная миграция существующих данных не требуется.
